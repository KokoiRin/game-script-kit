## Context

本地 UI 当前展示脚本步骤、依赖和可运行性检查。依赖摘要是面向人阅读的字符串，例如 `状态: 主页`；如果前端直接解析这些字符串来填充 dry-run 状态，会把展示格式变成隐式 API，后续调整中文文案时容易破坏交互。

## Goals / Non-Goals

**Goals:**

- 让 UI 能从选中脚本获得结构化的界面状态依赖。
- 让用户一键把脚本依赖的状态填入 dry-run 模拟状态输入。
- 保持 HTTP adapter 薄，只做 payload 转换，不解释脚本语义。

**Non-Goals:**

- 不引入完整的脚本变量系统。
- 不改变 `ScreenStateIs` 的执行语义。
- 不处理多个状态依赖之间的选择策略，先使用首次出现的状态依赖。

## Decisions

- 在 `ScriptDetailsResult` 中增加 `state_dependencies` 字段，而不是让前端解析 `dependencies` 文案。这样脚本语义分析仍留在 application 层，前端只消费明确字段。
- 状态依赖按脚本步骤遍历时的首次出现顺序去重。这样结果稳定、可预测，也符合脚本从上到下执行的阅读顺序。
- UI 操作先选择第一个状态依赖。多个状态依赖的下拉选择属于更完整的调试工作台能力，本轮不提前扩展。

## Risks / Trade-offs

- 多状态脚本只填第一个状态依赖 → 在按钮提示中保持行为简单，后续可以在同一结构化字段上升级为选择菜单。
- HTTP payload 增加字段 → 这是向后兼容新增字段，不影响现有调用方。
