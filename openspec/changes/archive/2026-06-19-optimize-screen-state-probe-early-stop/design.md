## Context

当前 `locate_many(...)` 已经做到一次截图匹配多张模板，但仍会无条件匹配所有模板。日志中的 4 个候选每个匹配约 0.38-0.44 秒，平均一轮约 2.1 秒；如果扩展到几十个场景，单轮耗时会线性增长。

用户的当前诉求是：命中某个场景后不再继续看后面的候选。这个优化必须落在真实匹配循环里，否则只能改变结果选择，不能减少 OpenCV 匹配耗时。

## Goals / Non-Goals

**Goals:**
- `locate_many(..., stop_on_first_match=True)` 找到第一个命中模板后停止匹配后续模板。
- 未执行的后续模板在返回结果中标记为 skipped，方便日志说明本轮为什么没有候选耗时。
- 状态探测默认启用早停，按候选顺序确定当前状态，而不是继续计算所有候选的最高置信度。

**Non-Goals:**
- 不做窗口区域配置。
- 不做模板缓存、多尺度匹配、并行匹配或图像金字塔。
- 不做命中频率统计或 UI 图表。
- 不改变单图 `locate(...)`、`ImageExists(...)`、`Click(ImageTarget(...))`。

## Decisions

1. **早停放在 batch locator，而不是只放在 engine。**
   - 理由：只有 desktop adapter 知道一张截图内逐模板匹配的循环，早停放在这里才能真正少跑 OpenCV 匹配。

2. **候选顺序就是优先级。**
   - 理由：用户未来会有几十个场景；用 assets 排序和后续配置排序表达优先级，比“全匹配后取最高置信度”更可控，也更快。

3. **用 skipped 表达未执行候选。**
   - 理由：调用方仍能拿到与输入候选同长度的结果，UI 日志也能解释后续候选不是未命中，而是本轮没必要匹配。

## Risks / Trade-offs

- 早停会牺牲“多个候选同时命中时选最高置信度”的旧行为 -> 通过 OpenSpec 明确改为优先级顺序；这更符合用户对“找到就不用继续”的期望。
- 候选顺序当前来自文件名排序 -> 后续如果需要更精细优先级，可以增加配置文件；本轮不引入配置系统。
- 未命中场景仍要扫描全部候选 -> 这是正确性需要，后续可通过区域裁剪或二级粗筛优化。
