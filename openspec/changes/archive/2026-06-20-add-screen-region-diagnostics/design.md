## Context

本地控制 UI 已经有截屏诊断接口 `/api/capture-screen`，可以保存并展示当前屏幕截图；界面状态探测已经从 `assets/screen-states.json` 读取命名区域和状态搜索项。当前缺口是：用户只能从日志推断区域是否正确，无法在截图上直接看到这些区域。

## Goals / Non-Goals

**Goals:**
- 在 UI 中提供一个明确入口，生成带命名区域框的诊断截图。
- 复用现有截图 adapter 和 `screen-states.json` 解析规则，避免 UI 直接理解状态配置细节。
- 诊断图保存到项目调试目录，并通过现有截图预览机制展示。
- 保持状态探测、图片匹配和脚本执行语义不变。

**Non-Goals:**
- 不在本轮实现交互式拖拽框选区域。
- 不自动修改 `assets/screen-states.json`。
- 不新增状态识别 DSL 或脚本变量语义。
- 不解决所有截图性能问题。

## Decisions

1. **诊断图生成放在 application 层。**
   HTTP adapter 只新增一个 POST endpoint，静态 UI 只负责触发和展示结果；状态配置读取、截图保存、绘制区域框由 `LocalControlApplication` 编排。这样符合“入口薄、规则收进用例”的项目原则。

2. **复用已有截图能力，先保存原始截图，再生成诊断图。**
   诊断图需要和当前真实画面对应。用例调用现有 `screen_capture_factory` 生成截图，再基于该截图绘制区域框，避免增加新的平台 adapter contract。

3. **区域坐标按当前匹配 adapter 的点坐标语义绘制。**
   `screen-states.json` 中的区域已经用于真实匹配，匹配 adapter 会按截图像素和鼠标点坐标比例换算。诊断绘制也应根据截图尺寸和屏幕点尺寸做同样换算，避免“诊断图看起来对但匹配实际不对”。

4. **第一版只绘制命名区域。**
   状态搜索项可以引用命名区域，也可以内联区域。当前用户最需要校验的是长期配置的命名区域；内联区域后续可在配置管理能力更成熟时扩展。

## Risks / Trade-offs

- [Risk] 屏幕点尺寸获取失败会导致区域框无法精确换算。→ Mitigation: 第一版允许注入测试用的屏幕尺寸工厂；真实桌面装配使用 `pyautogui.size()`，失败时返回清晰错误。
- [Risk] 配置中没有命名区域时，诊断图对用户帮助有限。→ Mitigation: 返回配置错误，提示没有可绘制区域。
- [Risk] UI 按钮增多可能让脚本控制区拥挤。→ Mitigation: 先放在图片诊断工具栏，后续再按功能分组优化 UI。
