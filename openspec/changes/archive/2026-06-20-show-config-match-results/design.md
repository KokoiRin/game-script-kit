## Context

本地 UI 已有两个数据来源：

- `/api/screen-state-config` 返回状态组、搜索项、图片、区域和最低置信度。
- `/api/screen-state-probe` 返回最近一轮候选结果，候选结果包含状态名、搜索项名、状态、置信度、最佳置信度和最佳位置。

目前页面把这两块分开展示。用户想判断某个配置搜索项是否有效时，需要在两个区域之间手动对照名称。

## Goals / Non-Goals

**Goals:**

- 状态配置摘要直接显示每个搜索项最近一次探测结果。
- 探测状态更新后，配置摘要自动重新渲染。
- 没有最近结果时，配置摘要明确显示“最近：暂无”。

**Non-Goals:**

- 不修改 `assets/screen-states.json` 格式。
- 不新增 HTTP endpoint 或改变 payload。
- 不改变状态探测算法、早停逻辑或命中判定。

## Decisions

1. **在前端关联配置和候选结果。**
   - 理由：两个 payload 已经包含足够字段，关联逻辑只影响展示；保持 HTTP adapter 和 application 层不变。
   - 备选：由 application 层返回合并后的配置状态摘要。当前没有多入口复用需求，会增加后端模型和转换代码。

2. **使用 `state + search_name` 作为匹配键。**
   - 理由：状态组内搜索项名称来自配置，候选结果也保留同一搜索项名称，能避免不同状态下同名搜索项互相覆盖。
   - 备选：只用 `search_name`。如果不同状态复用同名搜索项，页面会展示错误结果。

3. **配置 payload 和最近候选 payload 都缓存到前端状态。**
   - 理由：任一数据源更新后都能重新渲染配置摘要，不需要重复请求配置。

## Risks / Trade-offs

- [Risk] 早停候选会展示为跳过，用户可能误以为配置失效。→ Mitigation：显示“跳过”，区别于“未命中”。
- [Risk] 如果配置变更后未刷新页面，最近结果可能来自旧配置。→ Mitigation：本轮只做只读展示；后续做配置编辑时再引入版本或刷新机制。
