## Context

当前识图能力以 `ScreenImageLocator.locate(...)` 为 seam，脚本侧已有 `ImageExists(...)` 和 `Click(ImageTarget(...))`。这些能力适合判断单张图或点击目标，但“判断当前处于哪个界面”是观察型工具，不应让 UI 直接解释脚本语义，也不应把多界面判断塞进 `ScriptRunner`。

第一轮实现以最小闭环为目标：使用 `assets/` 下的图片作为候选界面，每张图片对应一个界面名称；用户在 UI 中开启探测后，后端每轮执行一次多候选匹配，打印最新识别结果，等一轮结束后再按间隔开始下一轮。

## Goals / Non-Goals

**Goals:**
- 提供 application 层可测试的“探测一次”和“后台循环探测”用例。
- 每轮探测输出 `current_state`、每个候选的 `found/confidence/elapsed_ms` 和本轮总耗时。
- UI 新增一个 tab 展示界面探测能力，可启动、停止和轮询日志。
- 保持分层：HTTP 入口只做请求/响应转换，真实截图仍由外层装配的 `ScreenImageLocator` 完成。

**Non-Goals:**
- 不新增脚本 DSL，例如 `ScreenIs(...)` 或 `WaitUntilScreen(...)`。
- 不做复杂配置文件、自然语言编译器或状态机。
- 不在本轮优化为“一次截图匹配多模板”的新 adapter contract；第一轮允许复用现有 `locate`，先验证产品形态。
- 不做游戏窗口区域选择；后续可基于实际误判和耗时再加。

## Decisions

1. **先做工具用例，不改脚本语义。**
   - 理由：界面探测是观察型能力，第一轮需要调素材、阈值、日志和 UI 展示；直接进入 DSL 会把尚未稳定的语义固化。
   - 替代方案：新增 `ScreenIs("装备界面")` 条件。暂不采用，因为这会跨 DSL、runner、脚本资源配置等多处，范围过大。

2. **第一轮以 `assets/` 图片名作为界面名。**
   - 理由：用户现在已经把模板素材放在 `assets/`，最少配置即可使用；例如 `装备.png` 显示为 `装备`。
   - 替代方案：新增 JSON/YAML 界面配置。暂不采用，因为现阶段主要验证识别是否有用，配置系统可等候选变复杂后再做。

3. **循环探测由 application 管理后台会话。**
   - 理由：和已有后台脚本运行类似，UI 需要启动、停止、查询日志；application 能控制同一时间只跑一个探测会话并归一化结果。
   - 替代方案：浏览器每秒 POST 一次探测。暂不采用，因为真实匹配可能超过 1 秒，浏览器定时请求容易堆积并发匹配。

4. **每轮结束后再等待下一轮间隔。**
   - 理由：避免匹配慢时积压，并符合用户提出的“每轮结束了就截一张新的图”的期望。

## Risks / Trade-offs

- 匹配多张图片会较慢 -> 第一轮明确打印每轮和每个候选耗时，后续再决定区域裁剪或 batch screenshot 优化。
- 仅用图片名当状态名表达力有限 -> 后续可以新增配置文件，把一个状态绑定多个素材并设置权重。
- 现有 `ScreenImageLocator.locate` 每个候选可能各截一次图 -> 第一轮接受这个成本，避免为了优化提前改变 port contract。
