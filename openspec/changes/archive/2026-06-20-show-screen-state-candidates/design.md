## Context

领域层的一轮 `ScreenStateProbeResult` 已包含候选详情：候选名称、是否命中、置信度、耗时和 skipped 状态。后台循环探测目前只把这些结果用于日志和累计统计，HTTP 状态接口没有结构化暴露最近一轮候选详情。

## Goals / Non-Goals

**Goals:**

- 后台界面探测会话快照保留最近一轮候选结果。
- HTTP 状态 payload 暴露该候选结果，供 UI 直接展示。
- UI 在界面探测 tab 展示最近一轮候选命中、跳过、未命中、耗时和置信度。

**Non-Goals:**

- 不改变 `probe_screen_state` 的候选排序、早停或选择规则。
- 不新增图像匹配 adapter 能力。
- 不在前端解析日志文本来推导候选结果。

## Decisions

- 在 application 层新增只读 DTO 表达候选摘要。
  - 理由：HTTP adapter 和 UI 需要稳定的展示形状；直接暴露领域对象会让 entrypoint 知道过多内部结构。
  - 备选：HTTP adapter 直接遍历 `ScreenStateCandidateResult`。该方式会把转换逻辑放到入口层，不符合薄 adapter 约束。

- 后台会话只保存最近一轮候选摘要，不保存完整历史。
  - 理由：UI 当前需要的是“刚才为什么识别成这个状态”，完整历史会带来内存和展示复杂度。
  - 备选：保存最近 N 轮。后续如果需要趋势分析，可以在现有 DTO 上扩展，但当前不提前做。

- UI 用文本列表展示候选结果。
  - 理由：当前界面探测 tab 已以文本摘要和日志为主，列表足够表达调试信息，避免引入额外布局复杂度。

## Risks / Trade-offs

- 候选列表可能较长 → 继续复用可滚动日志/摘要区域附近的文本展示，后续可再做筛选。
- 置信度可能为空 → UI 明确显示“无”，避免把未命中误解成 0 分。
