## Context

当前界面状态探测已经支持后台循环、候选早停、配置区域和 UI 日志展示。日志适合排查单次匹配细节，但不适合让 UI 或后续脚本稳定读取“探测质量”：例如一共跑了多少轮、哪个状态经常命中、哪些候选因为早停被跳过、最近一轮耗时是多少。

## Goals / Non-Goals

**Goals:**
- 在 application 层为后台探测会话维护结构化统计。
- 通过现有探测状态查询 API 返回统计，让前端直接展示。
- 保持统计来源为已完成探测轮次，不影响当前状态判定和匹配早停语义。

**Non-Goals:**
- 不实现历史曲线、持久化报表或外部指标系统。
- 不改变 `probe_screen_state` 的候选排序、早停和当前状态选择规则。
- 不让 UI 解析日志文本来反推统计。

## Decisions

- 统计放在后台探测会话对象内，而不是 `probe_screen_state` 返回值内。原因是单轮探测结果已经表达当前轮详情，会话级计数属于 application 后台运行状态；这样也避免 engine 层知道 UI 轮询需求。
- HTTP payload 增加稳定 JSON 字段，前端直接渲染这些字段。相比继续增强日志，结构化字段更适合作为后续脚本状态面板或调试工具的基础。
- 命中统计按状态名累计，跳过统计按候选名累计。当前状态是状态级概念，命中频率按状态统计更贴近用户理解；跳过次数用于解释早停带来的“没有继续匹配”。
- 首版只维护内存统计，停止或重新启动探测后重新计算。当前目标是运行期调试，不需要跨会话累计。

## Risks / Trade-offs

- 统计字段会让 UI/API payload 稍微变大 → 统计只包含聚合计数和最近耗时，不包含完整历史。
- 早停后跳过候选可能和“未命中”混淆 → payload 和 UI 文案区分 skipped，日志继续保留每轮候选详情。
- 后台线程读写统计存在并发访问 → 沿用现有会话锁，在记录结果和生成快照时保护统计状态。
