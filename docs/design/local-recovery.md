# 循环内局部恢复与任务组织

- 状态为历史讨论稿，步骤树语法候选随 [ADR 0015](../adr/0015-python-only-tasks.md) 退役
- 日期：2026-10-18
- 本文不定义必须实现的语法、默认策略或开发门禁

2026-11-14 已采纳的 Python 函数任务使用普通异常处理组织局部恢复，当前接口见 [函数任务说明](../task-functions.md)。本文保留早期恢复方案的讨论背景。

## 要讨论的问题

用户反馈：循环里某一步失败会结束整个脚本；如果把每一段都拆成返回结果的脚本，又担心写法和理解成本上升。同时，用户如何描述任务、由 Agent 创建可维护脚本的路径仍需具体设计。

[由 Agent 创建和维护任务](../adr/0001-agent-authored-tasks.md) 已确定为协作方向；下列控制流和创建细节仍是候选，不因进入仓库而视为采纳。

## 当时的步骤树怎样运行

- 当时的 `ScriptRunner.run` 返回执行结果，运行用例和 Run Plan 已有结果归一化与汇总。
- 图片点击缺图、`WaitUntil` 超时会抛出 `ScriptStoppedNormally`，在最外层转为 `stopped_unmet_condition`，因而会退出整个脚本。
- `Repeat` 只接住自己 `break_if` 触发的局部中断，不接住上述条件停止。`If` 条件为假则选择 else，本身不终止脚本。
- 当时的嵌套循环与 `break_if_image` 可组合出部分局部退出，缺图或超时的恢复还需要另外设计。

因此缺口主要是局部恢复边界及恢复后的画面确认，并非系统完全没有返回结果。现有取消和窗口坐标限制另见 [当前状态](../current-state.md)。

## 先分清三种结果

| 层次 | 要回答的问题 | 例子 |
| --- | --- | --- |
| 动作执行 | 输入或识别调用执行了什么，外部能力是否可用 | 已发送点击、图片未找到、权限不可用 |
| 条件与控制流 | 当前观察意味着走哪条路、等待或结束哪一段 | 未出现对话、退出本轮尝试、重新认屏 |
| 业务完成 | 用户目标是否达成 | 任务已接取、奖励已领取、页面出现消息 |

同一次“没找到图片”可以是正常分支，也可以是必需前提未满足。点击调用成功与脚本步骤结束都不能代替业务完成证据，见 [结果与验收决策](../adr/0003-results-and-verification.md)。

## 为什么不能统一继续或重试

继续下一步默认前一步的结果仍成立：对话未出现就点“确认”，可能操作到另一画面。重试当前动作默认重复没有额外影响：第一次点击可能已经成功，只是反馈晚到，再点可能撤销、重复领取或重复发送。

从头开始也默认已回到起点；实际可能已进入任务、战斗或对话。可讨论的恢复方案都需要回答“当前在哪个可识别画面，下一步为什么在这里成立”，不能仅凭错误类型猜测。

## 三个候选

| 候选 | 作者的心智负担 | 恢复正确性的依据 | 较适合的场景 |
| --- | --- | --- | --- |
| A：局部尝试与恢复 | 给一小段步骤命名，说明预期条件不满足后退出哪段、怎样恢复 | 只处理明确声明的可恢复情况，认出恢复后的画面再继续 | 顺序稳定、偶尔等不到某一步的短任务 |
| B：有结果的子任务组合 | 声明子任务起点、结束结果与调用方分支 | 子任务同时说明结束时的位置与证据，调用方按少量有意义结果选择 | 同一片段已在多个任务复用，或下一步确实依赖业务结果 |
| C：画面状态驱动 | 描述每个画面的动作、后续画面与未知状态处理 | 操作后重新认屏，按已识别状态决定下一动作 | 画面会随时跳转、断连或改变路径的流程 |

### A：局部尝试与恢复

候选表达是将“打开列表 → 选择任务 → 等对话”作为一次尝试。若没有等到对话，退出这一段，再判断能否识别起始页或列表；可识别时执行相应恢复，不能确认时结束运行。

它不要求每次点击都增加变量，但需要讨论退出作用域、可恢复情况和恢复失败如何表达。恢复分支一多，嵌套结构仍可能变得难读。尚未确定使用新块类型、已有条件分支还是其他语法。

### B：有结果的子任务组合

例如“接取任务”返回“已接取／今日已完成／无法确认”等确实改变下一步的结果，而不是让每个点击返回一个通用成功或失败值。任务边界、资源共享和结束画面的约定需要一起设计。

如果目前只有一条流程，过早拆分会增加调用关系和结果路由；只有重复步骤不等于已经形成稳定的可复用任务。

### C：画面状态驱动

例如短暂在线的页面先确认“等待连接／可输入／已断开”等状态，再决定操作。它比固定步骤更能应对跳转，但需要处理状态冲突、未知画面、等待期限和重复动作。

仅看“可输入”不能知道本轮是否已粘贴发送，可能还需要本轮执行记录或页面反馈。增加持续截图线程本身不解决这些语义问题；现有状态 reader 也不等于已有完整状态机。

## 当前建议与待讨论点

倾向先用 A 验证一次具体失败：有限的局部尝试、明确的恢复画面和停止理由，先不扩展为通用异常捕获系统。若主要任务的画面变化非常频繁，C 可能更合适；B 可等待第二个真实任务暴露复用需求。这仍是建议。

需要共同决定的内容包括：

- 预期可恢复的是缺图、超时、特定画面变化中的哪些情况；哪些情况应立即停止。
- 局部失败应退出步骤段、当前循环轮次还是整个任务；嵌套时如何让作者看懂。
- 重试对象、次数和等待期限，以及已发生部分副作用时如何避免重复操作。
- 用户取消如何穿过恢复、子任务和 Run Plan；取消后是否允许任何恢复动作。
- 是否需要业务结果及哪些结果真正影响调用方，而非默认让每个动作返回变量。

## 与创建任务的关系

可以拿同一次真实失败，分别用三个候选写出可读流程再比较。Agent 先根据用户描述整理目标、起点、关键画面、完成证据和等不到时的处理，再生成或修改当前脚本；这种具体创建路径也需要通过一个任务试用确认。

坐标记录和截图只能提供素材，不能自动推导任务意图或恢复策略。本文没有决定重建调试工作台、开发完整编辑器或永久采用某种脚本格式。
