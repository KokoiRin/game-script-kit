# 0010：低频窗口流及独立源证据

- 状态：accepted
- 日期：2026-11-06
- 来源：用户要求把性能探索中的窗口流接入观察，明确每秒2到5帧即可，无须15帧。

## 背景

命令截图与PNG往返占当前双素材观察的大部分成本。只把截图改成读缓存会破坏原先基于read开始时刻的新鲜度，并可能让同一帧完成两次确认。探索记录见[性能设计](../design/window-capture-performance.md)。

## 决定

macOS只读观察默认使用ScreenCaptureKit常驻单窗流，系统采集频率跟随观察选项，默认2Hz、可选5Hz，保留既有1Hz选项。没有隐藏的15Hz采集。准备截图和脚本状态reader保持各自契约，不消费观察缓存。

观察工作线程首次读取时启动系统流。原生回调使用独立串行dispatch队列，复制BGRA后及时释放surface；单槽只保留最新完整像素及源证明。所有素材仍共享同一张独立RGB图片。共享的BoundWindow固定初始CG窗口编号、PID、标题和逻辑尺寸；每次读取前后核对，回调另核对内容范围、像素比例和surface尺寸。

领域结果可携带FrameProof：源事件序号、映射到Python单调时钟的系统displayTime、complete或idle类型。原始系统时间去重先于时钟换算，避免换算抖动制造新证据。缺失或无效时间不能用回调到达时间代替。idle只有在已有有效像素、携带更新的系统事件时间时，才证明画面仍未改变；不能从失效槽恢复。

应用会话用源时间计算新鲜度，以不同源证据做连续确认。重复缓存不增加确认次数、不续期；界面改称“连续两次确认”。旧请求式probe没有源证明时，仍以该次read开始作为时间下界。处理成本、源事件年龄和UI当前年龄分开显示，最近源年龄分位也保持最多120次。

停止先关闭发布槽，再等待系统停流和串行回调队列屏障。只有成功回收才标STOPPED；回收失败保持停止中、拒绝重启并交由既有原生后台终止机制处理。启动失败不自动开另一条流，不静默回退到命令截图。

## 代价与边界

窗口流需macOS14+及项目macos可选依赖；原生壳的其他能力仍保持macOS13+。新鲜度继续使用既有max(2秒,3/频率)预算，低频画面年龄可能接近一个采集间隔；本轮不追求100ms门槛。匹配与截图源均仍只读，不驱动游戏输入。

本机验证覆盖真实后台线程、2/5Hz、重复启停、属性页往返及实际签名权限。静态idle的系统事件语义有fake覆盖，但尚未对完全静态游戏画面、锁屏恢复和小时级连续运行作最终验收。模拟回收失败不代替真实强制回收测试。

## 重审条件

出现长期资源增长、停流异常、静态画面频繁过期，或具体任务要求更低的确认延迟时，依据源时间与生命周期证据调整，不只降低显示耗时。
