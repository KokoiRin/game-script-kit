# 0001：围绕真实任务，由 Agent 创建和维护脚本

- 状态：accepted
- 日期：2026-10-18（本轮用户确认）
- 性质：产品方向与协作方式；不表示下述任务能力已经实现

## 背景

Star 已具备点击、识图、条件等待和循环等执行基础，但现有游戏脚本主要停留在任务入口，尚未形成可靠的日常任务闭环。

如果继续以通用自动化平台和调试工具数量衡量进展，会扩大维护面，却无法回答用户实际完成了什么。直接要求用户编写嵌套 JSON，也没有解决任务描述与脚本实现之间的距离。

## 决定

用户已确认先围绕一款游戏的日常任务形成闭环。以清楚的起点、正常过程、可观察完成结果和失败表现定义任务，再推进下一项。

主要协作方式是用户描述任务意图和结果要求，Agent 主动观察目标应用、采集必要素材、补齐流程，生成、解释和维护脚本。无法访问目标、缺少必要业务信息或存在结果取舍时，再请用户补充。用户不需要先掌握脚本语法才能提出任务。

当前继续使用已有 JSON 脚本与资源配置，不为了重启项目先做格式迁移。JSON 是当前实现选择，本记录不将其固化为永久格式。

通用可视化编辑器暂不优先；这是当前投入取舍，并非永久排除编辑器。局部失败恢复、任务组合和创建流程的具体设计仍需讨论，见 [讨论稿](../design/local-recovery.md)。

## 代价

- 近期覆盖的游戏和任务更少，需要在真实画面中反复核对结果。
- Agent 需要花时间观察目标和核对业务结果；用户仍需澄清必要的业务意图与选择，动作日志不能代替目标中的完成证据。
- 现有 JSON 的表达限制暂时保留；发现具体阻碍时再决定改模型还是改格式。

## 重审条件

当首个任务已经稳定使用、第二个任务暴露真实复用需求，或 Agent 维护方式持续造成明显配置成本时，重审组合方式、脚本格式和编辑工具。
