# Star 架构约束

修改源码、port contract 或模块职责前阅读本文件。这里保留项目的稳定设计原则；运行命令和使用方法见 [README](../README.md)。

## 依赖与职责

项目采用 ports-and-adapters：核心规则保持可测试、可移植，真实设备、平台权限、HTTP、CLI 和 UI 的副作用留在外层。

用例调用的主要方向为：

```text
入口 → 平台装配 → 应用用例 → 执行/规则 → 领域模型
```

真实 adapter 在装配处注入，实现核心或应用层声明的 port；核心只调用 port，不导入 adapter。入口可以接收装配好的用例，而不必每次请求都经过装配函数。

| 角色 | 职责 | 项目中的位置 |
| --- | --- | --- |
| 领域模型 | 概念、不变量、不可变步骤和值对象；不执行副作用 | `portable/domain/` |
| 执行/规则 | 解释步骤、评估条件、调用 ports；不创建真实 adapter | `portable/engine/` |
| 应用用例 | 编排一次用户意图、归一化结果、通过注入接收外部能力 | `portable/application/` |
| Adapter | 实现 port，隐藏平台库、权限、设备与环境差异 | `platform/` 中的 adapters，以及 `portable/adapters/` 中的平台无关替身 |
| 装配 | 选择并注入真实或模拟实现 | `platform/local_desktop/composition.py` |
| 入口 | 解析 CLI/HTTP 输入、调用用例、展示结果 | `platform/local_desktop/entrypoints/` |

表中路径以 `src/game_automation/` 为根。新增平台或运行方式时，通过 adapter/composition 接入，跨平台核心不感知 macOS、桌面 UI 或终端环境。

## 接口与模块深度

- 每个 module 有清晰接口和单一主职责，按角色而非目录名判断归属。
- 接口包括调用方必须知道的类型、不变量、错误结果和调用顺序。新增接口应收拢复杂度，让调用方学习更少。
- 做删除测试：删除 module 后，复杂度若会散落到多个调用方，说明它有深度；如果只少一层转发，就应审视是否需要这层。
- 一个文件出现多种独立变化原因时，优先拆分职责。暂不拆分时用分隔注释标明区域。
- 扩展受阻时，在已触达的范围内提炼接口、收拢重复规则、拆分职责或移动逻辑；重构应服务于当前需求，而非目录美化或猜测未来功能。

## 需要重审的信号

- CLI/UI/HTTP handler 开始解释脚本语义或业务规则。
- 领域或执行层开始知道平台、权限、真实设备或入口细节。
- 同一规则散落在多个调用方，或新增能力要求同步修改很多无关文件。
- 测试依赖 private method、内部调用次数或临时实现结构。
- 文件职责需要很长的文字才能解释清楚。

遇到这些信号，先明确规则归属，把复杂度收回负责该规则的 module。跨越较大范围时，记录问题、接口与取舍，再推进实现。

## 已有的重要行为边界

- `Script` 保存步骤树并绑定单个坐标窗口；`ScriptRunner` 解释步骤，文件脚本 loader 负责 JSON 到领域对象的转换。
- `InputDevice` 是输入设备接缝，负责点击、拖拽、等待和组合键。组合键的按下与释放由 adapter 一次完成，执行器不持有按键状态。`KeyStateReader` 用于坐标记录工具读取按键，与模拟键盘输出不同。
- `run_script` 归一化单脚本结果，`run_script_plan` 编排命名脚本。正常停止仍可能有退出码 0；是否完成必须同时看 `finish_reason`，不能单看退出码。
- `star_visual_lab` 是独立目标应用。真实自动化从页面像素识别并操作；验收程序读取真值 API 判断结果，避免只用 Star 自己的成功日志证明成功。
